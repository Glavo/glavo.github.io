在很长一段时间里，Java 主要服务于传统的服务器环境。
Java 服务往往直接运行在系统上，能占用的资源也较为固定。

为了适应这种场景，Java 程序往往需要静态地通过 `-Xms` 和 `-Xmx` 选项来配置堆大小。
Java 在通过 GC 回收内存后，往往也会长期占用很多空闲内存，从而提高内存分配性能，以及减少 GC 的回收频率，提高吞吐量，改善程序性能。

但是现在 Java 的适用环境越来越多，这种静态的策略导致 Java 程序配置起来复杂，
难以灵活适应不同场景，而且还留下了吃内存大户的骂名。

在近期，OpenJDK 社区将精力集中在了这方面，开始通过一系列 JEP 来解决这个问题：

- [JEP 草案: G1 GC 的自动堆大小调整](https://openjdk.org/jeps/8359211)
- [JEP 草案: Serial GC 的自动堆大小调整](https://openjdk.org/jeps/8350152)
- [JEP 草案: 使 ZGC 实现更快的启动和预热](https://openjdk.org/jeps/8329758)

简单来说，在不远的未来，Java 程序不再需要手动指定 `-Xms` 和 `-Xmx` 选项。
默认的 `-Xmx` 将会是系统内存的 100%，Java 程序可以像 C 程序一样按需使用内存。

JVM 将会在运行时更智能地自动调整堆大小，而不会像之前那样有一个静态的较大的 `-Xmx`。

在程序空闲，或者系统内存不足时，JVM 会自动收缩堆，把内存归还给系统，让 Java 程序占用的内存更少，不再是吃内存大户；
而在程序需要更多内存时，Java 也能够自动扩展堆，直至占用所有系统内存，像 C 程序那样有良好的扩展性。

此外，Java 还会引入新的快速扩展堆的机制，大大改善程序的启动和预热速度，以及更好地应对突发的内存需求。

[根据一些测试](https://openjdk.org/jeps/8329758#Case-study-in-faster-startup-and-warmup)，
在应用这些改进后，示例服务器的启动时间降低了 38%，预热时间降低了 90%。

在这些修改后，用户基本不再需要通过 JVM 参数来调优了，不过对于剩下的少了必要情况，JVM 也提供了更简单的方式来控制 GC。

对于 G1 GC，用户可以通过一个新的 `-XX:G1GCIntensity` 选项来表达自己对 CPU 占用与内存占用之间的偏好。
默认情况下 JVM 会选择一个均衡的设置，但用户也可以手动调整它，
来选择是让程序更频繁的 GC 以减少内存占用，还是让程序使用更多内存来减少 GC。
用户也可以在运行时按需动态调整该选项。

可以说 Java 的下个 LTS (29) 将是一个重要的里程碑。其中不仅包含这些 GC 的重大改进，
还会有大家期待已久的 Project Valhalla，
甚至 Project Leyden 的 AOT 编译大概率也能正式发布。
Java 终于可以告别启动慢、内存占用大等顽疾，走向一个全新的阶段了。
