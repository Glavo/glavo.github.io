## 摘要

在使用 G1 GC 时，根据环境自动动态调整最大 Java 堆大小。

## 目标

在使用 G1 GC 时：

* 动态调整最大 Java 堆大小以适应环境中可用内存的变化。
* 典型性能与用户正确手动调整 Java 堆大小时相比不应有明显变化。

## 非目标

此 JEP 的目标不包括：

* 找到静态的最佳最大 Java 堆大小。
* 移除现有的通过配置 Java 堆大小调整静态堆边界的选项。
* 更改现有的根据工作负载动态调整当前 Java 堆大小的功能。

## 动机

当用户选择 G1 GC 时，他们唯一需要设置的与内存相关的选项就是最大堆大小。
不幸的是，想设置合适的最大堆大小是出了名的困难。
应用程序的内存占用可能取决于输入，并且在执行的不同阶段会发生变化，
但用户必须预先为应用程序设置一个最大堆大小，而且这个大小必须适用于程序的整个运行阶段。

除了 Java 堆内存外，JVM 本身也需要为自身分配一些内存，而且这也取决于所选的最大堆大小，
用户在确定最大堆大小时也需要考虑这一点。

如果最大 Java 堆大小设置得太低，应用程序可能会内存不足；如果设置得太高，环境可能会内存不足。
想要找到一个合适的最大堆大小，需要在具有代表性的工作负载的实验环境中测量应用程序内存使用和吞吐量。
对于大多数用户而言，搭建这样一个实验环境本身就是一个挑战。

我们认为，JVM 可以自动控制最大 Java 堆大小，并且能够比用户通过显式配置手动调整更好地平衡 CPU 和内存消耗。

JVM 应该监控环境中可用的空闲内存，并利用这些实时信息自动确定最大堆大小。
当用户选择 G1 GC 时，他们再不需要设置 `-Xmx`。
G1 GC 应该像 C 程序一样，在必要时可以使用环境中的所有内存，同时也可以及时响应可用内存的减少。

最后，用户应该能够表达自己偏好让 GC 的 CPU 消耗更低（但占用更多内存）还是偏好让程序占用更少内存（但会提高 CPU 占用率）。

通过自动堆大小调整，内存消耗可能还会取决于环境中的可用内存量。
如果环境中其他应用占用的内存较少，那么当前应用可能会使用更多内存；
如果其他应用程序使用了更多内存，那么当前应用可能会减少内存占用；

## 描述

G1 将能够自动选择最大 Java 堆大小，这个大小可以根据程序和环境中的变化动态调整。

自动选择的堆大小将在最小（`-Xms`）和最大（`-Xmx`）堆配置之间。
如果用户使用 G1 GC 且未配置这些选项时，JVM 会使用新的最大和最小堆大小默认值，
以便为自动堆大小调整提供尽可能多的灵活性。

新的默认最大堆大小和最小堆大小如下：

* 默认最小和初始堆大小（`-Xms`）为 4 MiB。
* 默认最大堆大小（`-Xmx`）为计算机可用内存与压缩 oops 边界（适用于启用了 `CompressedOops` 特性的情况，通常此边界约为 32GiB）中的较小值，再减去一个小的保留大小。

在这些边界内，G1 将动态调整 Java 堆大小：

* G1 会根据环境中可用空闲内存的变化[自动动态调整](#自动动态调整)最大堆大小。
  具体的[响应环境内存压力](#响应环境内存压力)的方式有两种：
  
  1. 在环境中空闲内存减少时，降低最大堆大小并将内存返还给操作系统，从而减少 JVM 的内存使用；
  2. 在环境中空闲内存增加时，增加最大堆大小并占用更多内存，从而改善 G1 GC 的性能。

* 当应用程序的内存分配速率突然增加时，G1 会通过[快速扩展](#快速扩展) Java 堆来应对。
* 提供一个[新方法](#g1gcintensity)（`-XX:G1GCIntensity`）让用户可以表达对性能/内存占用权衡的偏好，以影响动态的最大堆大小。

通过这些更改，使用 G1 GC 时用户手动配置 Java 堆大小的需求将显著减少，

使用 G1 GC 时，此功能将默认启用。由于 G1 GC 目前是默认的 GC，最终用户通常无需执行任何操作即可从这些更改中受益。

如果用户已经设置了最小和最大堆大小（通过 `-Xms` 和 `-Xmx`），那么这些设置会决定新功能的适用范围。
我们建议用户移除删除这些选项。

### 自动动态调整

在确定了初始最大堆大小后，G1 会持续监控 GC、应用程序和环境的行为来调整最大堆大小，
并会使用现有的机制对实际堆大小进行增量调整。

### 确定最大堆大小

G1 ergonomics 将使用环境中 100% 的可用内存确定最大堆大小，
并会遵守当前的[压缩 oops](https://wiki.openjdk.org/display/HotSpot/CompressedOops) 设置。
如果用户未手动设置最大堆大小，JVM 还会再减去少量保留内存。

开启压缩 oops 后，如果没有启用其他选项，那么内存使用上限大约为 32 GB。
由于应用程序所需堆内存通常小于 32 GB，默认情况下 G1 会将最大堆内存限制在此边界内，
从而充分利用压缩 oops 带来的性能优势。
如果用户禁用了压缩 oops，那么 G1 可以使用环境中除了少量保留内存之外的所有可用内存。

即使仅部署单个应用，JVM 为系统保留一部分内存也是很有帮助的。
例如，它可以用于填充文件缓存，从而提升系统性能。
同时，正如[快速扩展](#快速扩展)部分所述，这些保留内存可以作为安全缓冲区，
避免应用程序内存分配速率突然上升时 GC 出现意外响应（比如 Full GC）。

### 测量 CPU 开销

G1 是一种分代 GC。年轻对象被放置在年轻代中，并会被更频繁地回收。老年对象会被提升到老年代，一开始不会回收它们。
根据 [G1 GC 周期](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html#GUID-F1BE86FA-3EDC-4D4F-BDB4-4B044AD83180)，老年代的回收频率较低。

为了决定是否要扩展或收缩堆，G1 会跟踪 GC 的 CPU 使用情况，
并尝试将 GC 的 CPU 使用率保持在 `-XX:GCTimeRatio` 的当前值，
并会根据 `-XX:G1GCIntensity`、当前最大堆大小和其他现有变量进行调整。

在现有的启发式方法中，G1 会在每次年轻代回收时检查整体 GC CPU 使用率。
如果一系列 GC 消耗的 CPU 超过了目标 CPU 使用率，则会增加堆大小；
如果一系列 GC 消耗的 CPU 少于该 CPU 目标，则会减少堆大小。

垃圾回收活动并不是 GC 带来的唯一 CPU 开销。频繁的回收周期还会给应用程序带来其他 CPU 开销，
例如会增加 GC 屏障（在 GC 期间访问 Java 对象时执行的指令）的执行次数。
应用程序自身消耗的 CPU 越多，这些影响就越大。
现有的自动堆大小调整启发式方法会考虑到它们，并通过扩展堆以最小化这些影响。

### 响应环境内存压力

JVM 进程可以根据给定的目标 GC CPU 使用率自动找到合适的堆大小。
然而，如果我们允许 JVM 随意使用内存，那么环境中可能没有足够的内存来运行其他进程。
因此，除了监控 Java 应用程序的行为，G1 还会持续监控环境中的可用内存。
如果环境中的可用内存减少，G1 会调整其内部的目标 CPU 使用率并尝试减少堆大小。
同样地，当环境中的可用内存增加时，G1 可能会增加 JVM 的内存使用量，以更好地满足 GC CPU 使用率和暂停时间的目标，
以适应应用程序的当前和未来预测行为。

Java 堆的收缩和扩展会与应用程序并发进行；添加的内存会被主动地、并发地解除提交或提交，并进行分页处理，
以最小化由于系统操作引起的性能下降。

这种新的最大堆大小将自动考虑 JVM 内部使用的本机内存：
如果 JVM 需要更多的本机内存，那么 JVM 也会调整可用内存的大小，
自动确定的最大堆大小也会随之变化。

在同一环境中运行的其他应用程序也可能会耗尽环境中的可用内存，这将导致 GC 频率增加，
通过消耗更多 CPU 来减少内存占用，从而收缩堆。
环境中如果有多个使用 G1 GC 的 JVM 实例在并行运行，那么它们会达到平衡状态，
而不是相互争夺内存。

在启用内存压缩的 macOS 或 Windows 平台上，G1 会持续监控压缩和未压缩内存的比率，
并根据该比率调整保留的内存空间大小。
当操作系统开始压缩更多内存时，GC 将更加努力地回收垃圾并将内存返还给操作系统，从而缓解系统的压缩内存压力。

### 快速扩展

对于像 G1 这样的平衡型 GC 来说，良好的启动性能非常重要。
当 JVM 在具有许多核心的大型计算机上以 4 MB 的初始堆大小启动时，
它很快就会发现 Java 堆大小不够。

应用程序可能需要像 20 GB 这样较大的堆大小，而在这种情况下，GC 需要非常快速的扩展堆大小。

尤其是在启动阶段，由于初始的堆大小较小，应用程序对内存的需求可能会超过 GC 的回收速率，
导致 GC 会很早且很频繁地被触发。

为了应对应用程序内存分配激增的情况，G1 将根据现有的启发式算法不断扩展堆。

除了在分配激增的情况下扩展堆外，GC 还会根据 GC 自身以及应用程序最近的 CPU 使用率，按需扩展堆。
扩展堆能够让 G1 降低回收频率，减少 GC 的 CPU 占用，进而可能提高应用程序的吞吐量。

### G1GCIntensity

用户对于不同应用，可能会对 GC CPU 使用率与内存占用之间的权衡有不同的偏好。

新的 JVM 选项 `-XX:G1GCIntensity` 它接受一个介于 `0` 和 `10` 之间的整数，默认值为 `5`。

它会影响 GC 在 CPU 使用率与内存占用之间的权衡。
提高该值会让 GC 更倾向于使用更多的 CPU 来减少内存占用；
降低该值会让 GC 更倾向于使用更少的 CPU 来增加内存占用。

`-XX:G1GCIntensity` 选项是可管理的，这意味着如果需要，那么可以在运行时更新该选项的值。

## 测试

此增强功能主要影响性能指标。因此，它将通过各种工作负载进行彻底的性能测试。定义的成功指标将在上述工作负载上进行测试。

## 风险和假设

通过将默认最大堆大小从可用内存的 25% 更改为所有可用内存，存在新启发式方法使用的内存比当前实现更多的风险，因此其他进程可能会内存不足。然而，即使使用 25% 的默认最大堆策略，当多个使用该默认值的 JVM 在同一环境中运行时，已经存在这种风险。此外，动态更新的最大堆大小很可能能够在超出环境的内存限制之前抛出内存不足错误。
